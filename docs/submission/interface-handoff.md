# Задание на интерфейс NORTH

Документ определяет поведение будущего интерфейса, а не визуальный стиль. Макеты, frontend и BFF ещё не созданы. Контракт: [OpenAPI](../../api/openapi.json). Проверенный рабочий пример последовательности вызовов: [scripts/demo.py](../../scripts/demo.py).

## Граница первой версии

Один демонстрационный владелец, один зарегистрированный агент, одно действующее поручение на одну покупку, три предложения из каталога. На каждом экране обозначить «Тестовый режим — реальные деньги не списываются». Агентский сценарий в текущем demo исполняется детерминированным скриптом. Нельзя показывать чат с якобы действующей LLM или поиск по реальным магазинам: они не подключены.

Текущий каталог: PS5-Pro; 96 900 ₽ — превышает лимит; 81 000 ₽ — продавец не отмечен проверенным; 82 990 ₽ — подходит. Лимит 85 000 ₽, одна покупка, новое состояние товара, срок один час. Эти значения являются синтетическим стендом, а не рыночными ценами.

## Экраны и действия

| Экран | Что должен понять пользователь | Действия и фактические данные |
| --- | --- | --- |
| Создание поручения | Что именно агент сможет купить и на каких условиях | Форма условий, срок, число покупок; создание draft через POST /v1/mandates |
| Подтверждение | Каким агенту и условиям выдаётся право | Показать возвращённые сервером mandate.terms, подтвердить соответствующий digest через POST /v1/mandates/approve |
| Проверка предложений | Почему одно предложение подходит, а другое нет | Каталог GET /v1/offers; для каждого POST /v1/authorizations; показать policy.rules и reason_code |
| Покупка | Разрешение получено, затем платёж исполнен или ещё проверяется | POST /v1/payments с неизменными grant и transaction; GET статуса до финального состояния |
| История и управление | Что произошло и можно ли ещё отозвать поручение | GET /v1/audit, GET мандата; отзыв или полный возврат отдельными командами |

Никаких выдуманных остатков на счёте, графиков экономии и счётчиков клиентов. Каталог и статусы приходят с API. Изображения товара могут быть добавлены позже как иллюстрации с корректными правами; они не являются данными, проверяемыми текущим backend.

## Архитектура подключения

Для публичного стенда нужен серверный BFF между браузером и NORTH. Владелец и агент должны иметь раздельные серверные операции и credentials. Секрет владельца, agent_token, ключ подписи и callback key не встраивать в JavaScript, localStorage или общедоступные файлы. BFF аутентифицирует пользовательскую сессию и разрешает только соответствующие действия; агентский компонент не получает полномочия владельца. Не делать универсальный proxy с произвольным выбором роли клиентом.

Предпочтительно обслуживать frontend и BFF на одном origin, использовать защищённую серверную сессию и защиту изменяющих запросов от CSRF. Текущий NORTH не реализует браузерный login или CORS-политику для публичного SPA. Это задачи будущего подключения, а не уже готовые свойства интерфейса. Общий публичный токен владельца для всех посетителей недопустим: текущий sandbox не обеспечивает отдельный независимый demo-аккаунт каждому посетителю. Для записи достаточно локального стенда.

## Последовательность основного сценария

Регистрация агента: владелец вызывает POST /v1/agents с `{}`. Сохранить agent_id и agent_token на серверной стороне. Сформировать terms и создать поручение. Отобразить фактически возвращённые сервером условия; только после действия владельца отправить agent_id, mandate_id и digest в /v1/mandates/approve. Изменение условий после отображения требует нового draft или replace и нового подтверждения.

От имени агента запросить предложения. TransactionV1 собрать из точных полей предложения, дополнив идентификаторы поручения и агента, schema_version=1, action=purchase и purpose из утверждённых условий. Отправить в /v1/authorizations. HTTP 200 здесь ещё не означает разрешение: необходимо прочитать policy.decision. При DENY оплаты нет. При ALLOW сохранить grant и точную transaction на сервере, затем передать их в /v1/payments.

Начальный результат платежа PENDING. Получить payment_id и опрашивать GET /v1/payments/{id}, например раз в секунду с постепенным увеличением интервала. После 30 секунд показывать, что результат ещё уточняется, сохраняя возможность последующего чтения. Не превращать клиентский таймаут в FAILED и не создавать новую логическую покупку. Успех отображать только по SUCCEEDED. Затем прочитать мандат и показать consumed_uses=1, reserved_uses=0, state=CONSUMED.

## Соответствие API и ролей

| Операция | Метод и путь | Роль |
| --- | --- | --- |
| Регистрация / отзыв агента | POST /v1/agents ; POST /v1/agents/revoke | Владелец |
| Создать / заменить поручение | POST /v1/mandates ; POST /v1/mandates/replace | Владелец |
| Подтвердить / отозвать поручение | POST /v1/mandates/approve ; POST /v1/mandates/revoke | Владелец |
| Получить поручение | GET /v1/mandates/{id} | Владелец или соответствующий агент |
| Каталог | GET /v1/offers?product=PS5-Pro | Аутентифицированный участник |
| Авторизация / исполнение | POST /v1/authorizations ; POST /v1/payments | Только агент |
| Статус платежа | GET /v1/payments/{id} | Владелец или соответствующий агент |
| Риск-согласие | POST /v1/challenges/approve | Только владелец |
| Создать / читать возврат | POST /v1/refunds ; GET /v1/refunds/{id} | Только владелец |
| Журнал | GET /v1/audit | Только владелец |

В текущем контракте нет GET списков агентов, поручений и платежей. Для компактного demo серверная сессия хранит созданные ID; источник актуального состояния — соответствующий GET. Полноценный кабинет со списками требует дополнительных API, пагинации и отдельной приёмки. /v1/audit возвращает последние 200 событий владельца, не бесконечный архив. Нельзя выдавать существующий журнал за готовую аналитику всех операций.

## Читаемые состояния

| Код | Текст интерфейса | Поведение |
| --- | --- | --- |
| DRAFT | Поручение ожидает подтверждения | Предложить проверить условия |
| ACTIVE | Поручение действует | Показать срок и доступное число покупок |
| REVOKED | Поручение отозвано | Новое исполнение не предлагать |
| EXPIRED | Срок поручения истёк | Создать новое поручение |
| CONSUMED | Разрешённая покупка выполнена | Повторная покупка требует нового поручения |
| PENDING | Платёж ожидает обработки | Читать статус |
| SUBMITTED | Платёж передан на исполнение | Не обещать отмену внешней операции |
| UNKNOWN | Результат платежа уточняется | Сверка; не показывать повторную оплату |
| SUCCEEDED | Тестовый платёж выполнен | Прочитать состояние мандата |
| FAILED | Платёж отклонён | Показать подтверждённый исход |
| CANCELLED | Платёж отменён до исполнения | Не показывать списание |

Возврат имеет отдельный refund_id и state. Успешный возврат не восстанавливает использованное право покупки. Статус исходного платежа может оставаться SUCCEEDED; показывать возврат отдельным результатом.

## Ошибки и причины

| Код | Текст |
| --- | --- |
| AMOUNT_LIMIT_EXCEEDED | Стоимость покупки превышает установленный лимит |
| MERCHANT_NOT_VERIFIED | По условиям поручения требуется проверенный продавец |
| MERCHANT_NOT_ALLOWED | Этот продавец не входит в список разрешённых |
| OFFER_MISMATCH | Предложение изменилось или не совпадает с каталогом |
| PRODUCT_MISMATCH | Товар не соответствует поручению |
| MANDATE_EXPIRED | Срок поручения истёк |
| USAGE_LIMIT_EXHAUSTED | Доступное число покупок исчерпано или зарезервировано |
| TRANSACTION_HASH_MISMATCH | Параметры покупки изменились после выдачи разрешения |
| IDEMPOTENCY_OR_STATE_CONFLICT | Запрос конфликтует с ранее сохранённым действием; обновите состояние |
| DENIED | Действие не разрешено; проверьте полномочия и состояние поручения |
| RATE_LIMITED | Слишком много запросов; повторим после паузы |

Не уточнять общий DENIED до «повторный платёж», если это не подтверждено состоянием: код используется для нескольких причин. Для policy отображать reason_code только у rules с passed=false; поле failure у успешно пройденного правила не означает фактический отказ.

При ASK_USER показать конкретные параметры покупки и запрос согласия. Передать owner-командой agent_id, mandate_id, challenge_id и точный transaction_hash. Затем повторить авторизацию агентом с новым Idempotency-Key. Такое согласие не отменяет жёсткие ограничения суммы, срока и проверенного продавца. Основной demo использует allow_risk_approval=false; этот сценарий оставить дополнительным.

## Денежные значения и повторы

API принимает целые копейки: 85 000 ₽ = 8 500 000; 82 990 ₽ = 8 299 000. Времена — Unix seconds UTC; показывать пользователю локальное время с зоной. Не вычислять денежные значения через неточное умножение дробных JS Number без проверки. Для demo значения безопасны в Number; для общего int64-контракта предусмотреть ограничения диапазона или lossless parsing.

Каждая логическая POST-команда получает свой Idempotency-Key длиной 1–128 ASCII-символов без пробелов. Сетевой повтор того же действия использует тот же ключ и неизменное тело. Новое решение или изменённое тело — новый ключ. Кешированный ответ POST может оставаться PENDING; актуальное состояние берётся через GET. При неизвестном результате регистрации не выпускать нового агента, а повторить исходную регистрацию с тем же ключом.

## Приёмка после дизайна

Интерфейс принимается, когда пользователь создаёт и подтверждает реальное поручение, видит два объяснимых отказа и одну успешную sandbox-покупку, повтор не создаёт новый платёж, изменённая сумма отвергается backend, журнал соответствует действиям, UNKNOWN не изображается как отказ, а секреты отсутствуют в клиентской сборке. Перезапуск сценария создаёт новые ID без удаления истории. Сброс базы отдельной опасной кнопкой для посетителей не нужен.
