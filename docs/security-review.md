# Security review and implementation boundaries

Review scope: source, PostgreSQL role permissions and invariants, signed canonical data, API identity boundary, transaction/lock ordering, provider recovery, audit/outbox and local sandbox deployment. This is an implementation review, not an independent penetration test.

Financial domain/application packages depend on ports. PostgreSQL and sandbox provider adapters are separate, and the runtime composes them. The public API can create a durable payment command through enforcement; it does not expose Authorize/Capture/Refund provider methods to agents. The provider database role cannot read NORTH grants. The application role cannot modify offers or audit history. A narrowly scoped SQL SECURITY DEFINER function performs the authoritative offer row lock; it has a pinned search_path, no dynamic SQL and no PUBLIC execute permission.

Canonical terms are immutable after approval. Signatures are purpose-separated and key-bound; exact transaction digests include quantity, fees, shipping, product, category, condition, currency, merchant and offer revision. The grant binds a one-time risk approval when applicable. A valid signature alone never bypasses database revocation, expiry or usage checks. Policy is deterministic, traces all rules and cannot let risk consent override hard constraints.

Issuance reserves usage under agent/mandate row locks. Consumption is atomic with one durable command under a unique grant constraint. PostgreSQL, not Redis or a process mutex, owns correctness. Idempotency responses share the mutation transaction. Idempotency request locks precede domain locks; standalone authentication audit writes complete before the business transaction, avoiding an audit-head/agent lock inversion. SQL transactions have bounded lock, statement and idle timeouts.

Submission rechecks all policy inputs and is the cancellation linearization point. Provider calls run outside the NORTH transaction. The sandbox provider persists authorization/capture/refund state with stable keys and at most one capture. A timeout after capture leaves NORTH UNKNOWN and keeps the reservation; reconciliation observes the committed provider state. Final accounting and audit commit together. Callbacks verify HMAC, payload binding and event-ID deduplication; state cannot regress. Refunds never replenish the mandate.

HTTP rejects duplicate/unknown JSON fields, invalid UTF-8, oversized bodies and inappropriate owner/agent roles. Credentials are not logged. Registered credentials are stored as hashes; idempotent registration responses do not persist the plaintext agent token. The demo owner token/signing seed stay in ignored local configuration. Global and per-principal token buckets bound request load and limiter memory. OTel traces include normalized routes rather than raw URLs or bearer headers; metrics are owner-protected.

Audit records are append-only to the app and hash chained. Verification checks the chain, persisted head and an optional external checkpoint. Outbox relay uses SKIP LOCKED and deduplicates durable inbox delivery atomically. The schema's counters/unique constraints are additional defenses; they do not replace application authorization or make a compromised bank runtime trustworthy.

Important limits: sandbox opaque credentials are not OIDC; sandbox Ed25519 is not a certified HSM integration; no real payment rail or merchant attestation is connected; key rotation and independent audit anchoring are not implemented; no claim is made of exactly-once external delivery to arbitrary providers. See production-roadmap.md. Client-disconnected or infrastructure-failed requests cannot guarantee arbitrary external observability, but committed financial state changes require their audit record in the same transaction.

Review findings corrected during development: unavailable Go container tag (checksum-pinned distribution build); PostgreSQL FOR SHARE privilege requirement (narrow locker function); ambiguous timestamp parameter inference in retry arithmetic (explicit timestamptz); outbox availability tied to simulated business time (database publication clock); authentication audit lock ordering (standalone transaction); mutable risk-approval grant column (database guard); ambiguous agent credential lookup (unique credential reference).
